## Goal

Build an **npm create initializer** that outputs a **production-oriented SaaS starter**.

### The initializer
- Package name: `create-saas-stack`
- CLI bin: `create-saas-stack`
- Canonical usage:
  - `npm create saas-stack@latest <target-dir>`
  - `npx create-saas-stack@latest <target-dir>`

### The generated SaaS starter MUST include
- Modern TypeScript full-stack app (Next.js App Router)
- Clerk authentication (email-first; no required OAuth providers)
- Supabase for Postgres + Storage (use it wherever sensible; do not use Supabase Auth)
- Stripe billing (hosted checkout + **webhooks as source of truth**)
- Loops.so lifecycle automation (event-driven; delivered via worker with retries)
- Docker-first deploy (portable; no provider lock-in)
- No GraphQL

### Quality bar
Output must be consistent, repeatable, and operationally boring:
- `pnpm dev` starts the web app
- `pnpm worker` starts the worker
- `pnpm typecheck`, `pnpm lint`, and `pnpm test` pass on a fresh install
- Docker builds succeed for web + worker

## Fixed, Opinionated Stack (No Alternatives)

### Language & Runtime
- TypeScript (strict)
- Node.js 24 LTS
- Package manager: pnpm

### Web App
- Next.js (App Router)
- Tailwind CSS
- shadcn/ui component library (Tailwind-based)

### Data
- Supabase Postgres (system of record)
- ORM: Prisma
- Validation: Zod (shared schemas across app/worker)

### Auth
- Clerk (identity + sessions + Organizations)
- Organizations are REQUIRED when `--orgs` is enabled.
- The app mirrors identity into Postgres:
  - upsert `User` by `clerkUserId`
  - upsert `Org` by `clerkOrgId`
  - upsert `OrgMember` by (`orgId`, `userId`)
> Multi-tenancy MUST be implemented using app-owned DB tables (`Org`, `OrgMember`) and route scoping.

### Payments
- Stripe (hosted checkout)
- Stripe webhooks are the source of truth for subscription state

### Email Automation
- Loops.so (event-driven lifecycle messaging)
- App emits events; worker delivers to Loops with retries

### Storage
- Supabase Storage
- Use signed upload URLs generated by server-side endpoints

### Background Jobs
- Postgres-backed queue using `pg-boss`
- Separate `worker` service (Node) consumes jobs
- Do not do heavy work inside the web request cycle

### Observability
- Sentry for error tracking (web + worker)

### Tests & Quality
- Unit: Vitest
- E2E: Playwright
- Lint: ESLint
- Format: Prettier

### Deploy (Fixed Choice)
- Docker (web + worker containers)
- CI/CD must be portable and not tied to a specific PaaS

## Architecture Principles (Hard Rules)

1. **App-mediated data access**
   - Web and worker use a server-side database connection via Prisma.
   - Do NOT rely on client-side direct DB access in baseline.
   - RLS policies may exist, but the template must remain safe without requiring complex RLS.

2. **Separation of concerns**
   - `web` handles UI + light request orchestration.
   - `worker` handles async: Stripe event processing, Loops events, retries, scheduled jobs.

3. **No “business logic in the database”**
   - DB stores facts and constraints.
   - Business logic lives in TypeScript services.

4. **Stripe truth comes from webhooks**
   - Redirect pages do not finalize billing state.
   - Always upsert billing state from webhook events.

5. **Everything must be idempotent**
   - Stripe webhook events: de-dupe by `event.id`
   - Jobs: de-dupe by idempotency keys
   - Loops calls: de-dupe by your `EmailEvent.id`

6. **Multi-tenant by default**
   - Template supports both B2C and B2B by enabling organizations (“orgs”) and membership.
   - B2C is the special case of a single “personal org” created on signup.

## Canonical Database Model (Prisma)

The generator MUST scaffold these baseline tables:

- `User`
  - `id` (uuid)
  - `clerkUserId` (unique)
  - `email`
  - `name` (nullable)
  - `createdAt`

- `Org`
  - `id` (uuid)
  - `clerkOrgId` (unique) — mirror Clerk Organization ID
  - `name`
  - `slug` (unique) — app-friendly URL slug
  - `createdAt`

- `OrgMember`
  - `id` (uuid)
  - `orgId` (fk)
  - `userId` (fk)
  - `clerkOrgMembershipId` (unique) — mirror Clerk membership ID
  - `role` ("owner" | "admin" | "member")
  - unique constraint (`orgId`, `userId`)

- `Subscription`
  - `id` (uuid)
  - `scope` ("org" | "user") — who owns the subscription
  - `orgId` (nullable fk)
  - `userId` (nullable fk)
  - `stripeCustomerId` (unique, nullable)
  - `stripeSubscriptionId` (unique, nullable)
  - `status` (string)
  - `plan` (string)
  - `currentPeriodEnd` (timestamp, nullable)
  - `createdAt`, `updatedAt`

- `StripeEvent`
  - `id` (uuid)
  - `stripeEventId` (unique)
  - `type`
  - `createdAt`
  - used for webhook idempotency

- `EmailEvent`
  - `id` (uuid)
  - `eventName`
  - `scope` ("org" | "user")
  - `orgId` (nullable)
  - `userId` (nullable)
  - `payloadJson` (json)
  - `status` ("pending" | "sent" | "failed")
  - `attempts` (int)
  - `lastError` (nullable)
  - `createdAt`, `updatedAt`

Additionally, `pg-boss` creates its own job tables. Allow that.


## Clerk Integration Requirements (Generated)

### Auth policy (Hard Rule: no gating)
- MUST support self-serve signup using email (password and/or email magic link).
- MUST NOT require Google/GitHub OAuth providers to be configured for baseline signup/login.
- OAuth providers may be OPTIONAL, but must not be required.

### Organizations (Hard Rule)
When `--orgs` is enabled:
- MUST use Clerk Organizations for:
  - org creation
  - org membership
  - invitations
  - membership roles (owner/admin/member)

### Web app behavior
- Middleware protects authenticated routes.
- On first login, web app must upsert `User` by `clerkUserId`.
- On first login, the app must ensure the user has a personal org:
  - Create a Clerk Organization if none exists for this user.
  - Mirror it into `Org` (`clerkOrgId`, `slug`, `name`).
  - Create membership record in `OrgMember` with role `owner`.

### Clerk webhook sync (Hard Rule)
- The generated app MUST include a Clerk webhook endpoint:
  - `/api/clerk/webhook`
- It MUST verify webhook signatures.
- It MUST upsert:
  - `User` (if user events)
  - `Org` (organization created/updated/deleted)
  - `OrgMember` (membership created/updated/deleted)

### Org scoping (Hard Rule)
To avoid “active org” ambiguity, org context is derived from the URL:
- All authenticated app pages are scoped by slug:
  - `/app/o/[orgSlug]/...`
- For each request:
  - Load `Org` by `orgSlug`
  - Verify the current Clerk user is a member of `Org` (via `OrgMember` or Clerk membership)
  - Enforce role via RBAC helper

### RBAC helper
Generate a shared RBAC utility that:
- checks org membership and role
- enforces role requirements on server actions / route handlers

## Stripe Integration Requirements (Generated)

### Hard choice (no ambiguity): webhook handled by web, processed by worker

The baseline implementation MUST do the following:

1. **`web` exposes `/api/stripe/webhook`:**
   - verifies Stripe signature
   - writes `StripeEvent` row (idempotent by `stripeEventId`)
   - enqueues a `pg-boss` job: `stripe.process_event` with minimal payload (`stripeEventId` + `type`)

2. **`worker` consumes `stripe.process_event`:**
   - fetches the Stripe event data from Stripe API **or** stores the raw event payload in DB at webhook time  
     **(choose ONE approach in implementation and be consistent)**
   - upserts `Subscription` state
   - emits lifecycle events by enqueueing `loops.send_event` jobs

### Must generate
- Server endpoint to create a Stripe Checkout Session (hosted checkout)
- Webhook endpoint at `apps/web/src/app/api/stripe/webhook/route.ts`
- signature verification
- idempotency via `StripeEvent` table (`stripeEventId` unique)

### Billing sync
Worker must upsert `Subscription` records:
- map customer + subscription IDs
- update `status` / `plan` / `currentPeriodEnd`
- emit lifecycle events for Loops (`trial_started`, `plan_changed`, `payment_failed`, etc.)

## Loops Integration Requirements (Generated)

### Event-driven pattern (Hard Rule)
- The app MUST NOT call Loops inline inside user requests.
- The app MUST enqueue Loops delivery through the worker.

Required flow:
1. Web/worker creates an `EmailEvent` row (status `pending`)
2. Web/worker enqueues a `pg-boss` job `loops.send_event` with `emailEventId`
3. Worker loads `EmailEvent` from DB, sends to Loops, updates status
4. Retries are handled by job retries + attempts counter on `EmailEvent`

### Default events to scaffold
- `user_signed_up`
- `org_created`
- `invited_member`
- `trial_started`
- `plan_upgraded`
- `plan_downgraded`
- `payment_failed`
- `subscription_canceled`
